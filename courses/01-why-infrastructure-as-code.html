Why infrastructure as code

Most data platforms start in a web console. Someone clicks a bucket into existence, someone else adds a catalog, a third person tightens a permission on a Friday, and six months later nobody can say what the platform is, only what it does when it breaks. Infrastructure as code turns that history into a file you can read, review and run again. Tonight you write the file: you separate what you want from what exists, meet providers and resources, and run Terraform's whole loop, init, plan, apply and destroy, on your own laptop at zero cost.

Part 0

Where we start

The running case is constructed. Larkspur Freight is an invented mid-size logistics company building its first data platform. Today it has a handful of storage zones and a catalog that two engineers created by hand in a cloud console, and a data lead, Priya, who has been asked by the board "what exactly do we run, and could we rebuild it?" She cannot answer either question from the console. Across six sessions Larkspur writes its platform down as Terraform code: tonight a first config, then the lake zones, the state, a reusable module, the review of a plan, and the gate that ships it. Everything runs locally with stand-in resources, so you can follow without a cloud account or a bill.

Part 1 · covers click-ops against infrastructure as code

A console remembers nothing you can review

5 min live

A cloud console is a fine way to learn what a service can do and a poor way to run a platform. Each click changes something real, and the only record is the thing itself. Infrastructure as code moves the source of truth into text: a file describes what should exist, a tool compares that description with what does exist, and a person reads the difference before anything changes.

LiveWhat click-ops costs a data team3 min▶

A console change has three properties that hurt later. It is invisible: the bucket's retention was set to 30 days by someone, at some time, for some reason, and the console shows only the 30. It is unreviewed: the change happens at the moment of the click, so the first reviewer is production. And it is unrepeatable: building the same platform in a second region, or rebuilding after an accident, means replaying hundreds of clicks from memory.

Data platforms feel this sooner than most systems because they are long-lived and full of state that matters: zones that hold years of files, catalogs that point at them, grants that decide who reads what. Larkspur's two engineers can each describe half the platform. Neither can describe all of it, and the console cannot either.

Self-studyWhat code buys, and what it does not3 min▶

Written as code, the platform gains what software already has: version history (who changed retention, when, and the pull request that says why), review before change, the same definition reused for dev and prod, and a rebuild that is a command rather than an archaeology project. HashiCorp's own exam objectives open with exactly this: explain what IaC is and the advantages of IaC patterns.

It does not make a change safe by itself. A config can describe a terrible platform precisely, and a plan nobody reads protects nobody. Session 5 is about reading plans well, and session 6 about making sure one is always read. Code also does not cover everything: an object created in the console stays outside Terraform until someone imports it, which session 3 shows.

Real world

The rebuild question. A familiar moment in any data team: an auditor or a new head of platform asks for an inventory of what runs in production and how each piece is configured. With click-ops the answer is a week of screenshots that are out of date by Monday. With code the answer is the repository, and the honest follow-up question becomes "is everything in it?", which is a much smaller problem.

Part 2 · covers desired state, recorded state and idempotence

Three versions of the truth, and the plan between them

5 min live

Terraform is declarative: you describe the end state, not the steps to reach it. To act on that description it keeps three things apart. The configuration says what you want. The real infrastructure is what exists. The state file is Terraform's record of which real object belongs to which block of your configuration. A plan is the difference between what you want and what exists, worked out through that record.

LiveDeclarative means you describe the end, not the steps3 min▶

A script says "create a bucket, then set retention to 30". Run it twice and you either get two buckets or an error. A declarative config says "there is a bucket with retention 30". Terraform works out the steps: create it if it is missing, change retention if it differs, do nothing if it already matches. The second run of the same config does nothing, and says so. That property, idempotence, is what makes it safe to run Terraform again and again in a pipeline.

You will see it in the build-along tonight: the second terraform plan prints "No changes. Your infrastructure matches the configuration."

Self-studyWhy a separate record at all3 min▶

Terraform cannot simply look at the cloud and guess which bucket is "the raw zone in your config". Many objects look alike, and names can change. The state file binds each resource address in your config, such as local_file.readme, to one real object and its id. Before every plan Terraform refreshes that record by asking the provider what the object looks like now, then compares your config against the refreshed record.

That record is powerful and easy to damage, which is why session 3 is spent entirely on it: what it holds (including secrets in plain text), where to keep it, how to lock it, and how to repair it without hand-editing.

Read every plan through the three boxes. When a plan surprises you, ask which box moved. Did someone edit the config (desired), did someone change the real thing in a console (actual), or did the record lose track of something (recorded)? Session 3 breaks each one on purpose.

Part 3 · covers providers, resources and the core loop

Providers, resources, and four commands

5 min live

Terraform itself knows nothing about buckets or warehouses. Providers are plugins that teach it one platform each: hashicorp/aws, hashicorp/google, snowflakedb/snowflake, databricks/databricks, and tonight two that run on any laptop, hashicorp/local and hashicorp/random. A resource block names a type from a provider and a local name, and that pair is the resource's address. The same four commands drive every provider, which is how one tool covers several clouds and services at once.

LiveProviders are plugins, pinned by version3 min▶

A required_providers block says which providers the config needs, where they come from and which versions are acceptable. terraform init finds a matching version in the public registry, downloads it into the hidden .terraform folder, and records the exact version and checksums it chose in .terraform.lock.hcl. HashiCorp's own advice, printed by init itself, is to commit that lock file so everyone and every pipeline gets the same provider. Session 4 covers version constraints and the lock file properly.

A resource block then uses a type from a provider: resource "local_file" "readme" has type local_file from hashicorp/local and local name readme. Its address, local_file.readme, is how plans, state and every later command refer to it.

Self-studyTerraform or OpenTofu on your laptop2 min▶

Two command-line tools read the same configuration language. Terraform is HashiCorp's, now owned by IBM, under the Business Source License since version 1.6.0. OpenTofu is the open-source fork under the Linux Foundation, released as a drop-in replacement in January 2024 and licensed MPL 2.0. For every build-along on these pages either works: type tofu where the page says terraform. Session 6 explains the split and what it means for a data team choosing one.

The outputs on these pages were produced by Terraform 1.17.1. Install it from HashiCorp's download page, or OpenTofu from opentofu.org, and check with terraform version or tofu version.

Real world

One tool, many platforms. A data team's platform rarely lives in one place: object storage in one cloud, a warehouse such as Snowflake, a lakehouse such as Databricks, and identity somewhere else. Each has its own Terraform provider, so one repository and one review process can describe all of them. Session 4 shows the same Larkspur zone module written against four of those providers, shown and not applied.

Build-along

A first config, through the whole loop

★ 22 min · everyone builds

Priya's first step for Larkspur is deliberately small: one random id that stands in for a platform build number, and one file that stands in for a real resource and uses that id. Both providers run locally, so nothing here costs money or touches a cloud. Make an empty folder, open a terminal in it, and follow along. Every output below was really run with Terraform 1.17.1; your ids and hashes will differ.

Write the config. Save this as main.tf. The terraform block pins two providers; the two resource blocks are the whole platform for now. The file's content refers to the id, which is how Terraform learns the order.

★ Step 1 · main.tfterraform { required_providers { local = { source = "hashicorp/local", version = "~> 2.5" } random = { source = "hashicorp/random", version = "~> 3.6" } } } resource "random_id" "platform" { byte_length = 4 } resource "local_file" "readme" { filename = "${path.module}/out/README.txt" content = "Larkspur Freight data platform, build ${random_id.platform.hex}\n" }

Initialise the directory. init reads required_providers, downloads matching versions and writes the lock file. It needs the network once; nothing is created yet.

★ Step 2 · terraform init (trimmed)$ terraform init Initializing the backend... Initializing provider plugins... - Finding hashicorp/local versions matching "~> 2.5"... - Finding hashicorp/random versions matching "~> 3.6"... - Installed hashicorp/local v2.9.1 (signed by HashiCorp) - Installed hashicorp/random v3.9.1 (signed by HashiCorp) Terraform has created a lock file .terraform.lock.hcl to record the provider selections it made above. Include this file in your version control repository ... Terraform has been successfully initialized!

Plan, and read it. The + symbol means create. Values Terraform cannot know until the object exists, like the random hex, read "known after apply". The last line is the one to read first.

★ Step 3 · terraform plan (trimmed)$ terraform plan Terraform used the selected providers to generate the following execution plan. Resource actions are indicated with the following symbols: + create Terraform will perform the following actions: # local_file.readme will be created + resource "local_file" "readme" { + content = (known after apply) + filename = "./out/README.txt" + id = (known after apply) ... } # random_id.platform will be created + resource "random_id" "platform" { + byte_length = 4 + hex = (known after apply) ... } Plan: 2 to add, 0 to change, 0 to destroy.

Apply. In class we pass -auto-approve to skip the yes prompt; in real work you read the plan and type yes, or apply a saved plan (session 6). Watch the order: the id is created before the file that uses it.

★ Step 4 · terraform apply$ terraform apply -auto-approve ... Plan: 2 to add, 0 to change, 0 to destroy. random_id.platform: Creating... random_id.platform: Creation complete after 0s [id=fyQSpw] local_file.readme: Creating... local_file.readme: Creation complete after 0s [id=7f976794dce28748ccac82819c2640f3f41a2aaf] Apply complete! Resources: 2 added, 0 changed, 0 destroyed. $ cat out/README.txt Larkspur Freight data platform, build 7f2412a7

Plan again: idempotence. Same config, nothing changed outside. Terraform refreshes both objects and finds nothing to do.

★ Step 5 · the second plan$ terraform plan random_id.platform: Refreshing state... [id=fyQSpw] local_file.readme: Refreshing state... [id=7f976794dce28748ccac82819c2640f3f41a2aaf] No changes. Your infrastructure matches the configuration.

Break the actual box by hand. Delete the file, the way someone might delete a bucket in a console, and plan. Desired did not change, actual did, so the plan puts it back. Apply to repair it.

★ Step 6 · drift, then repair$ rm out/README.txt $ terraform plan ... # local_file.readme will be created + resource "local_file" "readme" { + content = <<-EOT Larkspur Freight data platform, build 7f2412a7 EOT ... Plan: 1 to add, 0 to change, 0 to destroy. $ terraform apply -auto-approve ... Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

See the graph, then destroy. terraform graph prints the dependency Terraform inferred, in the DOT format graph tools read. Destroy walks it backwards: the file goes before the id it depends on.

★ Step 7 · graph and destroy$ terraform graph digraph G { rankdir = "RL"; node [shape = rect, fontname = "sans-serif"]; "local_file.readme" [label="local_file.readme"]; "random_id.platform" [label="random_id.platform"]; "local_file.readme" -> "random_id.platform"; } $ terraform destroy -auto-approve ... Plan: 0 to add, 0 to change, 2 to destroy. local_file.readme: Destroying... [id=7f976794dce28748ccac82819c2640f3f41a2aaf] local_file.readme: Destruction complete after 0s random_id.platform: Destroying... [id=fyQSpw] random_id.platform: Destruction complete after 0s Destroy complete! Resources: 2 destroyed.

Keep the folder. Session 2 grows it into Larkspur's lake zones. If you destroyed everything, that is fine: terraform apply rebuilds it from the file in one command, which is the whole argument of tonight in a single line.

Homework

Before session 2

30 min
  1. Change the content and plan. Edit the sentence inside content and run terraform plan. Read the symbol it uses and the line ending in # forces replacement, and write one sentence on why a file cannot be edited in place by this provider.
  2. Open the lock file. Read .terraform.lock.hcl and find the exact provider versions init chose. Delete the .terraform folder and run terraform init again: does it pick the same versions?

Check yourself

Three questions

Clear all three and session 1 gets stamped in your passport.

1 · You apply a config, then run terraform plan on the same config. Nobody changed anything in between. What does the plan show, and why?

A declarative tool describes the end state, so once actual matches desired there is nothing left to do, and the plan reads "No changes. Your infrastructure matches the configuration." Note the contrast: plan itself never changes anything, so two plans with no apply between them would both list the same additions.

2 · Someone deletes Larkspur's README file by hand. Which of the three boxes moved, and what does the next plan do?

The config still says the file should exist, and refresh reads the real world before the diff, so the plan shows "1 to add". C is the common misunderstanding: Terraform does not trust the state blindly; it refreshes it first.

3 · In the build-along, why is random_id.platform created before local_file.readme?

A reference is a dependency, and Terraform builds a graph from the references. Declaration order in the file does not matter; session 5's bench shuffles the blocks to prove it. Resources with no dependency between them can run in parallel.
