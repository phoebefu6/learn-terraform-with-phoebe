The HCL language

Last session's config had one id and one file, both written out by hand. A real data platform has zones per environment, settings that differ between dev and prod, a password that must never be printed, and things other teams built that you need to read but not own. HCL, the language Terraform configs are written in, has a small set of tools for exactly that: variables and validation, locals, for_each, outputs and data sources. Tonight you meet each one, then use all of them to lay out Larkspur's lake zones, and run the one experiment that explains why experienced engineers reach for for_each before count.

Part 1 · covers blocks, arguments, types, variables, outputs and locals

Blocks, arguments, and the values that flow between them

5 min live

Every Terraform file is made of blocks, and every block follows the same grammar: a block type, zero or more labels, then braces holding arguments and sometimes more blocks. Learn that one shape and the whole language reads the same way, whether the block declares a provider, a resource, a variable or an output. Values then move between blocks by reference, and that movement is what makes one config serve several environments.

LiveBlocks and arguments: the grammar in one picture3 min▶

Seven block types carry almost everything you will write. terraform holds settings such as required_providers. provider configures a plugin. resource declares something Terraform creates and owns. data declares something Terraform only reads. variable is an input, output is a value the config hands back, and locals names an intermediate value so you write it once. Inside the braces, an argument is name = expression; a nested block, such as validation inside a variable, has its own braces and no equals sign.

Every value has a type. The primitive ones are string, number and bool. The collections are list (ordered, by position), map (by key) and set (unique, unordered), and object describes a structure with named attributes of their own types. Larkspur's zones are a map(object({ retention_days = number })): one key per zone, each carrying its own retention. That one type declaration is what lets Terraform reject a zone with retention written as "thirty" before anything runs.

Values travel by reference: var.env for a variable, local.prefix for a local, local_file.zone["raw"].filename for a resource attribute, data.local_file.raw_marker.content for a data source. Formatting is not a matter of taste either: terraform fmt rewrites files into the canonical layout, and session 6 turns it into a check every change must pass.

Self-studyValidation and sensitive4 min▶

A validation block inside a variable has two arguments: a condition that must be true, and an error_message shown when it is not. Larkspur allows exactly two environments, so the condition is contains(["dev", "prod"], var.env). In the build-along, passing -var env=staging stops the plan with "env must be dev or prod.", and Terraform names the rule and the line that rejected it. A bad value never reaches a resource.

sensitive = true is narrower than it sounds. On a variable or output it hides the value in plan and apply output: the build-along prints warehouse_password = <sensitive>. It does not keep the value out of the state file. HashiCorp's own documentation says "Terraform stores values with the sensitive argument in both state and plan files." When the build-along's state file was searched for the fake password with grep -c, the count was 1. Session 3 opens that file and finds it in plain text. Real secrets belong in a secrets manager such as Vault, which this session only names.

Variable validation is one of several custom conditions. Resources, data sources and outputs can also carry precondition and postcondition checks, added in Terraform 1.2.0; they are named here and not built.

Real world

The environment nobody planned. A familiar story on platform teams: someone types stagging or Prod on the command line, and the config happily builds a third set of resources with a misspelled name, which then sits there costing money until someone notices it in a bill. A one-line validation on the environment variable turns that into an error before the plan exists, which is the cheapest place an error can ever appear.

Part 2 · covers count against for_each

Name instances by key, not by position

5 min live

Both count and for_each turn one resource block into several instances. The difference is how each instance is named in state. count names them by position: [0], [1], [2]. for_each names them by key: ["raw"], ["curated"], ["serving"]. Positions move when a list changes; keys do not. For anything that holds data, that difference decides whether a small edit removes one zone or quietly rewrites another.

LiveWhy for_each keys survive a reordered list3 min▶

The build-along's last step runs this for real. One variable holds ["raw", "curated", "serving"]. Resource by_index uses count over it; resource by_key uses for_each over the same list turned into a set. After applying both, remove "curated" and plan.

The count resource still has a [0] and a [1], it just has no [2] any more. So Terraform reports by_index[1] "will be updated in-place" with input = "curated" -> "serving", and by_index[2] "will be destroyed", with the reason printed underneath: "because index [2] is out of range for count". The for_each resource reports one line: by_key["curated"] "will be destroyed" because the key "is not in for_each map". The combined plan reads "Plan: 0 to add, 1 to change, 2 to destroy."

With stand-in resources that is harmless. With a storage zone it means the object that held curated data is now told to be the serving zone, and the object that really was serving is deleted. You asked for one removal and got a rewrite plus a deletion of the wrong thing.

Self-studyWhen count is still right2 min▶

HashiCorp's count documentation draws the line clearly: "Use the count argument when you want to create nearly identical instances", and "Use for_each when some instance arguments must have distinct values that can't be directly derived from an integer index." Three interchangeable worker nodes are nearly identical; three data zones with different names and retention are not.

count also has one job it does better than anything else: switching a single resource on or off. count = var.enable_audit_zone ? 1 : 0 creates the resource when the flag is true and none when it is false. There is only ever one instance, at [0], so nothing can shift.

One practical note for for_each: it takes a map or a set of strings, not a list. That is why the experiment wraps the list in toset(...), and why Larkspur's zones are declared as a map from the start.

Real world

A data zone overwritten by an index shift. A pattern that shows up whenever storage is created from a list with count: someone retires the middle entry, the plan says "1 to change, 1 to destroy", it looks small, and it gets approved. What it actually did was repoint one zone's settings at another's name and delete the last one in the list. Reviewers who know the difference read the address, not the count of changes: a [1] being updated where you expected a removal is the tell. Zone design itself (raw, curated, serving) is covered in Learn Data Warehouse with Phoebe.

Part 3 · covers expressions, for expressions and data sources

Expressions shape values; data sources read them

5 min live

An expression is anything on the right of an equals sign: a literal, a reference, a string with ${...} interpolation, a function call, a conditional, or a for expression that builds a new collection from an old one. A data source is the other half of reading: instead of computing a value inside the config, it asks a provider for something that already exists, and Terraform never creates, changes or destroys it.

LiveExpressions: interpolation, references, for3 min▶

Interpolation puts expressions inside a string: "${path.module}/lake/${local.prefix}-${each.key}/ZONE.txt" builds each zone's path from a built-in value, a local and the current for_each key. Inside a for_each block, each.key is the map key ("raw") and each.value is its object, so each.value.retention_days reads that zone's retention.

A for expression builds a new collection by walking an old one. Larkspur's output zone_paths is { for k, f in local_file.zone : k => f.filename }: for each key and instance of the zone resource, keep the key and the filename. The result is a small map anyone can read without knowing the resource's internals. Functions do the rest: contains checks the environment in the validation, trimspace strips the trailing newline from the raw marker before it is printed, and toset turns a list into a set for for_each.

Self-studyData sources read, never write3 min▶

data "local_file" "raw_marker" asks the local provider to read a file and expose its content. It is declared with data, addressed as data.local_file.raw_marker, and in a plan it carries its own symbol: <= read (data resources). Terraform will never create, change or destroy the thing it reads. That is the whole point: the object belongs to someone else, or to another part of the config, and you only need its attributes.

Normally a data source is read during plan. Here its filename refers to a resource that does not exist yet, so Terraform cannot read it early, and the plan says so in two lines: "will be read during apply" and "(depends on a resource or a module with changes pending)". In the apply output you then see the file created first and the read afterwards.

In real platforms a data source is how one team's config uses another team's objects, such as an existing network, a shared key or a catalog, without taking ownership of them. Who may read what is an access-design question; Learn Data Access Control with Phoebe covers it.

Real world

The hard-coded id that outlived its object. A familiar failure: a config pastes in the id of a network or bucket another team created, the other team rebuilds it, and the pasted id now points at nothing. A data source that looks the object up by name on every plan removes the copy, and when the lookup fails it fails at plan time, in front of a reviewer, instead of half-way through an apply.

Build-along

Larkspur's lake zones, per environment

★ 22 min · everyone builds

Priya lays out the lake: one folder per zone, named for the environment, each holding a marker file with its retention. A validated environment variable, a map of zones, a local prefix, a for_each resource, a data source and three outputs: every idea from tonight in one file. Start in a fresh folder; everything runs locally with hashicorp/local and the built-in terraform_data, and works the same with tofu. Every output below was really run with Terraform 1.17.1 and hashicorp/local 2.9.1; your ids, hashes and times will differ.

Write the config. Save this as main.tf in an empty folder, then run terraform init as in session 1. The password default is deliberately fake and obviously so; never put a real secret in a default.

★ Step 1 · main.tfterraform { required_providers { local = { source = "hashicorp/local", version = "~> 2.5" } } } variable "env" { type = string description = "Which environment to lay out" default = "dev" validation { condition = contains(["dev", "prod"], var.env) error_message = "env must be dev or prod." } } variable "zones" { type = map(object({ retention_days = number })) default = { raw = { retention_days = 30 } curated = { retention_days = 365 } serving = { retention_days = 90 } } } variable "warehouse_password" { type = string sensitive = true default = "not-a-real-secret" } locals { prefix = "larkspur-${var.env}" } resource "local_file" "zone" { for_each = var.zones filename = "${path.module}/lake/${local.prefix}-${each.key}/ZONE.txt" content = "zone=${each.key} env=${var.env} retention_days=${each.value.retention_days}\n" } data "local_file" "raw_marker" { filename = local_file.zone["raw"].filename } output "zone_paths" { value = { for k, f in local_file.zone : k => f.filename } } output "raw_marker_text" { value = trimspace(data.local_file.raw_marker.content) } output "warehouse_password" { value = var.warehouse_password sensitive = true }

Validate. terraform validate checks syntax, references and types without touching anything or asking the provider about real objects. It is the cheapest check there is, which is why session 6 runs it on every pull request.

Check yourself

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · Three zones are created from the list ["raw", "curated", "serving"] with count. You remove "curated" and plan. What does count do that for_each would not?

count names instances by position, so after the removal [1] means "serving" and [2] no longer exists. The real run printed by_index[1] updated in place and by_index[2] destroyed "because index [2] is out of range for count", while for_each destroyed only by_key["curated"]. A is what people expect, and why the shift goes unnoticed in review.

2 · An output is marked sensitive = true. Which statement is accurate?

sensitive hides the value in plan, apply and output listings only. HashiCorp's documentation says sensitive values are stored in both state and plan files, and the build-along's state file contained the fake password. Whether state is encrypted at rest depends on where it is stored, which is session 3.

3 · A plan line starts with <=. What will Terraform do to that object?

The plan legend reads "<= read (data resources)". A data source only reads; here it was read during apply because its filename depends on a resource with changes pending. Replacement is -/+, update in place is ~, and importing is a separate step covered in session 3.
