Part 1 · covers what state holds and why secrets live in it

A ledger from address to real object

5 min live

Terraform cannot look at a cloud account and know which bucket is "the raw zone". The state file tells it. Every resource address in your config, such as local_file.zone["raw"], is written down next to the id of exactly one real object and every attribute Terraform last saw on it. Plans read this ledger, applies rewrite it, and anything stored in it, including values you marked sensitive, sits there as plain text.

LiveThe state binds addresses to real objects3 min▶

By default Terraform keeps state in a local file named terraform.tfstate in the working directory, and keeps the version before the last write in terraform.tfstate.backup. HashiCorp's state page is blunt about the file: "Do not directly edit this file." The reason is the binding. The JSON looks editable, but one wrong id silently points an address at a different object, and the next apply acts on it.

Instead the CLI gives you terraform state subcommands, and the docs say to use them "instead modifying the state directly". Every one that changes state writes a backup first, and those backups "can not be disabled". Two read-only ones are worth running daily. Real output from Larkspur's dev lake, run with Terraform 1.17.1:

★ Real run · state list and state show (trimmed)$ terraform state list local_file.zone["curated"] local_file.zone["raw"] local_file.zone["serving"] $ terraform state show local_file.zone["raw"] # local_file.zone["raw"]: resource "local_file" "zone" { content = <<-EOT zone=raw env=dev EOT ... filename = "./lake/larkspur-dev-raw/ZONE.txt" id = "2d18145fe7adc7af527ec22fec11794e1716e524" }

Read the last line: this provider uses a hash of the file's content as the object's id. Remember that; it explains a surprise in Part 3.

Self-studySecrets in plain text3 min▶

In session 2 Larkspur's warehouse_password variable and output were marked sensitive = true, and the CLI printed <sensitive> instead of the value. Then grep -c on the state file counted it once. That is documented behaviour, not a bug. HashiCorp's sensitive-data page says "Terraform stores your state in a plaintext file, which includes any secret values you defined in your configuration", and that values with the sensitive argument are stored "in both state and plan files". sensitive hides a value from the screen; it does not hide it from the file.

So treat the state file, and any saved plan file, with the same care as the secret itself. Whether it is encrypted at rest depends on where it lives: in HashiCorp's words, "the encryption method depends on your specific backend". OpenTofu took a different route and added optional end-to-end encryption for state files in its 1.7.0 release, covering state and plan files at rest, locally or in a backend.

Newer Terraform releases add ways to keep some values out of state altogether: ephemeral values in 1.10.0 and write-only attributes in 1.11.0, neither of which is persisted to state; both are worth reading about once the basics here are solid.

Real world

The state file in the wrong place. A familiar pattern: a team keeps local state, someone commits terraform.tfstate to the repository "so the others can use it", or attaches it to a support ticket to show a problem. The config had every secret marked sensitive and passed review. The state file carried the values in plain text to everyone with read access to the repository. The fix is structural, not a reminder: keep state in a backend with access control and encryption at rest, and keep *.tfstate out of version control.

Part 2 · covers backends and locking

One state, many hands, one lock

4 min live

A backend decides where state lives and who can reach it. On one laptop the local backend is enough. The moment two people, or a person and a pipeline, run Terraform against the same platform, the state has to be shared, and a shared file needs a rule for writers. That rule is the lock: whoever is writing holds it, and everyone else is turned away until it is released.

LiveRemote backends and the lock3 min▶

HashiCorp describes the local backend in one line: it "stores state on the local filesystem, locks that state using system APIs, and performs operations locally." A remote backend moves the file somewhere shared, such as an object store, so that every engineer and pipeline reads the same ledger. Locking is automatic where the backend supports it: "Terraform will lock your state for all operations that could write state." The same page warns that "Not all backends support locking", and leaves the detail to each backend's own page. Check it before you choose one.

Here is the lock doing its job, in the build-along's final step. Terminal 1 was applying; a teammate ran plan against the same state from terminal 2:

★ Real run · the second writer is refused (trimmed)$ terraform plan Error: Error acquiring the state lock Error message: resource temporarily unavailable Lock Info: ID: a57df1fa-e9d3-5082-3d28-df142f0623c2 Path: state/larkspur-dev.tfstate Operation: OperationTypeApply Who: <user>@<host> Version: 1.17.1 Created: 2026-11-03 04:11:24.330202 +0000 UTC ... Terraform acquires a state lock to protect the state from being written by multiple users at the same time. Please resolve the issue above and try again. For most commands, you can disable locking with the "-lock=false" flag, but this is not recommended.

The lock info tells you who holds it and since when, so you can ask them rather than guess. If a run crashed and left a stale lock, terraform force-unlock with that ID releases it. Use it only when you are sure the holder is gone: HashiCorp warns that "If you unlock the state when someone else is holding the lock it could cause multiple writers."

Self-studyS3 without DynamoDB3 min▶

For years the standard S3 backend recipe paired a bucket for the state with a DynamoDB table for the lock. That changed. Terraform 1.10.0 added S3 native state locking, and 1.11.0 made it generally available and deprecated the DynamoDB-related arguments. The current S3 backend page still says DynamoDB-based locking "is deprecated and will be removed in a future minor version": deprecated, not yet removed. Locking on S3 is opt-in through use_lockfile, which defaults to false, so a backend block without it does not lock at all.

S3 backend for Larkspur · shown, not appliedterraform { backend "s3" { bucket = "larkspur-terraform-state" key = "data-platform/dev.tfstate" region = "eu-west-1" use_lockfile = true encrypt = true } }

The bucket name and region are Larkspur's, constructed. Who may read that bucket is an access design question; the IAM side belongs to Learn Data Access Control with Phoebe, and the service itself to Learn AWS with Phoebe.

Real world

Two pipelines applying at once. A familiar pattern: a scheduled pipeline applies the data platform every night, and an engineer merges a fix that triggers a second apply while the first is still running. With a locking backend the second run fails fast with the lock error and the fix waits a few minutes. With a backend that does not lock, or an S3 block missing use_lockfile, both runs read the same starting state and the last one to finish overwrites the other's record. Nothing fails loudly; the state is simply wrong until someone notices drift.

Part 3 · covers drift and the repair tools

When the ledger and the world disagree

6 min live

State goes wrong in a small number of ways, and Terraform has a dedicated tool for each one. The skill is diagnosis: decide which of the three boxes from session 1 moved, desired, recorded or actual, and reach for the tool that moves the ledger without moving the world. Reaching for a text editor on the state file is never on the list.

LiveDrift and refresh-only plans2 min▶

Drift is the real world changing without Terraform: a console edit, a hotfix script, an expired object. A normal plan refreshes and then proposes undoing the drift. terraform plan -refresh-only, available since v0.15.4, does only the first half: it "creates a plan whose goal is only to update the Terraform state and any root module output values." It shows you what changed outside, and lets you decide whether to accept it into the record or overwrite it.

One lesson from the real run: the provider decides how drift reads. Someone appended a line to the raw zone's file. Because local_file uses a hash of the content as its id, a changed file is, to this provider, a different object, so refresh-only reports the original as deleted:

★ Real run · plan -refresh-only after a hand edit (trimmed)$ echo "edited in the console" >> lake/larkspur-dev-raw/ZONE.txt $ terraform plan -refresh-only ... Note: Objects have changed outside of Terraform Terraform detected the following changes made outside of Terraform since the last "terraform apply" which may have affected this plan: # local_file.zone["raw"] has been deleted - resource "local_file" "zone" { ... This is a refresh-only plan, so Terraform will not take any actions to undo these. If you were expecting these changes then you can apply this plan to record the updated values in the Terraform state without changing any remote objects.

A cloud bucket whose tags changed would instead show an in-place difference. Read drift reports in the provider's terms, not in your expectation of them.

Livemoved, import, removed, state mv and rm4 min▶

moved (Terraform 1.1.0) records a rename in code: "Use this block to programmatically change the address of a resource." The object stays where it is; only its address in the ledger changes, and "Terraform does not destroy the resource during the Terraform run."

import (1.5.0) adopts an object that exists but is not in state: you write an import block with the target address and the object's id, and the plan shows it will be imported. terraform plan -generate-config-out=PATH can even write the resource block for you, though the plan docs still mark that flag experimental. Since 1.7.0 an import block can use for_each to adopt many instances at once.

removed (1.7.0) records that a resource left the config. By default Terraform then destroys the object; with lifecycle { destroy = false } it removes it "from state without destroying the actual resource". destroy is the only lifecycle argument a removed block accepts.

Sketch · a removed block that keeps the object (not run)removed { from = local_file.lake_zone lifecycle { destroy = false } }

terraform state mv "changes bindings in Terraform state so that existing remote objects bind to new resource instances", and terraform state rm makes Terraform forget an object without touching it. They do the same jobs as moved and removed, but immediately, from one person's terminal, with no plan and no review. Prefer the blocks for anything a team shares; keep the commands for one-off repairs, and know that each one writes a backup first.

Self-studyNever hand-edit state2 min▶

HashiCorp says it three ways. The state page: "Do not directly edit this file." The state command page: use the terraform state commands "to modify the Terraform state instead modifying the state directly." And the state-in-CLI page explains the risk: "Modifying state data outside of normal terraform plan or terraform apply operations can cause Terraform to lose track" of the objects it manages.

The danger is that a hand edit is the one change with no safety net. It skips the plan that shows you the consequence, skips the backup the commands write, skips the lock if you edit a local copy of a remote state, and skips review. Every break on this page has a tool that does the same job with those protections intact. If you ever think you need a text editor, write down which box moved and look at the decision tree again.

Real world

The tidy-up rename. A familiar pattern: an engineer renames resources in a clean-up pull request so the names match the team's new convention. The code diff looks cosmetic. The plan, if anyone reads it, says every renamed object will be destroyed and created again, "because" the old address "is not in configuration". For a storage zone that means an empty new zone. The build-along reproduces exactly this, and one moved block turns it into a plan that changes nothing.

Build-along

Break it three ways, fix it

★ 22 min · everyone builds

Priya wants her team to have broken state on purpose, on a laptop, before it ever breaks for real. You will build three dev lake zones, then drift one, rename all three, lose a state file and contend for a lock, fixing each break with the matching tool. Everything uses hashicorp/local, hashicorp/random and the built-in terraform_data, and works the same with tofu. Every output below was really run with Terraform 1.17.1; your ids, hashes, lock IDs and times will differ.

Apply three zones and read the ledger. In a new folder, save this as main.tf, run terraform init and terraform apply -auto-approve, then list and show the state.

Check yourself

Three questions

Clear all three and session 3 gets stamped in your passport.

1 · You rename local_file.zone to local_file.lake_zone and change nothing else. There is no moved block. What does the plan propose?

Terraform matches config to state by address, not by content. The new addresses have no state, so they are created; the old ones have no config, so they are destroyed. The real run planned "3 to add, 0 to change, 3 to destroy". A moved block turns the same rename into "0 to add, 0 to change, 0 to destroy".

2 · Larkspur marks its warehouse password variable and output sensitive = true. Where can the value still be read in plain text?

HashiCorp's docs say Terraform "stores values with the sensitive argument in both state and plan files", and that state is a plaintext file. Session 2's grep found the value once in state. Protect state like the secret: an access-controlled backend, encryption at rest, never in version control.

3 · The state file was deleted, but the real object still exists, and the plan now wants to create it again. What is the right fix?

An import block adopts an existing object into state: the real run planned "1 to import, 0 to add, 0 to change, 0 to destroy" and applied "Resources: 1 imported". Applying the original plan would try to create a second object, hand-editing state is the one repair with no plan, backup or review, and state rm removes from state something that is not there.
