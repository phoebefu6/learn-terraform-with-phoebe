Learn Terraform with Phoebe · Session 5 of 6

Read a plan like a reviewer

A plan is the last moment anyone can stop a change before it happens, and most plans are approved after a glance at the summary line. Tonight you learn to read one properly: the symbols, the attributes that force a resource to be destroyed and rebuilt, the lifecycle settings that guard against that, and the dependency graph that decides what happens first. Then you use a plan simulator that computes every plan and apply order in your browser, and find the rung where "1 to add, 1 to destroy" means a zone full of data is gone.

Part 1 · covers plan symbols and the summary line

Six symbols, and the one line that hides them

4 min live

Every resource in a plan carries a symbol for what will happen to its real object. The summary line then counts them: "Plan: X to add, Y to change, Z to destroy." It counts a replacement twice, once as an add and once as a destroy, so a plan that reads "1 to add, 0 to change, 1 to destroy" may be a harmless swap of two unrelated resources, or one bucket being deleted and recreated empty.

LiveA reading order for any plan3 min▶

1. The summary line, for scale only. 2. Every -/+, +/- and -, by searching the plan for "must be replaced" and "will be destroyed". 3. For each replacement, the attribute marked # forces replacement: is that the change the author meant to make? 4. For each destroy, the reason line Terraform prints under it, such as "because local_file.zone is not in configuration": a rename without a moved block reads exactly like that. 5. Then the ~ updates, which are usually what the pull request said it was doing.

The order matters because the dangerous lines are short and the safe ones are long. An update to forty tags fills a screen; the destroy of a raw zone is five lines in the middle of it.

Self-studyWhere the symbols are written down2 min▶

HashiCorp's plan command page shows +, -, ~ and -/+ with an example ending "Plan: 2 to add, 1 to change, 2 to destroy." and an attribute annotated # forces replacement. The full legend, including +/- create replacement and then destroy and <= read (data resources), is printed by Terraform itself at the top of a plan that uses them; both appear in the real runs in sessions 2 and 5. The legend lists only the symbols that particular plan uses.

For a machine reader, terraform show -json on a saved plan gives the same information as a list of actions per resource, which is what policy tools read (Part 4).

Real world

The tidy-up rename. Renaming a resource block is the most common way a harmless-looking pull request destroys something. The code diff is one word. The plan says one resource will be created and one destroyed, "because it is not in configuration". Session 3 ran it for real: renaming three zones without a moved block planned "3 to add, 0 to change, 3 to destroy". With a moved block the same rename planned nothing at all. Rungs 2 and 3 of the bench below reproduce it.

Part 2 · covers force-new attributes and the lifecycle meta-argument

When a change means a rebuild, and three ways to steer it

5 min live

Some attributes cannot be changed on a live object. The provider marks them force-new: change one and the only way to get there is to destroy the object and create another. For storage that is the attribute that matters most, because a new bucket is an empty bucket. The lifecycle block, available on every resource, changes how Terraform handles that moment.

Liveprevent_destroy and create_before_destroy3 min▶

prevent_destroy = true makes Terraform reject any plan that would destroy the object, including a replacement. HashiCorp's docs add the caveat every reviewer should know: it does not stop a destroy when the resource configuration itself is removed, because the guard lives in the block that is being deleted. Real Terraform 1.17.1, on a stand-in resource whose region changed:

★ Real run · prevent_destroy$ terraform plan Error: Instance cannot be destroyed on main.tf line 1: 1: resource "terraform_data" "raw_zone" { Resource terraform_data.raw_zone has lifecycle.prevent_destroy set, but the plan calls for this resource to be destroyed. To avoid this error and continue with the plan, either disable lifecycle.prevent_destroy or reduce the scope of the plan using the -target option.

create_before_destroy = true flips the order of a replacement: the new object first, then the old one, now called "deposed". It shortens downtime for things like a server behind a load balancer. For a bucket it does not save the contents, and it fails if the name must be unique and both would exist at once. The same change, swapped to create_before_destroy, really applied:

★ Real run · create_before_destroy+/- create replacement and then destroy ... terraform_data.raw_zone: Creating... terraform_data.raw_zone: Creation complete after 0s [id=6675ecfc-259a-be0a-cbdd-2b7d54838823] terraform_data.raw_zone (deposed object d29179ca): Destroying... [id=41e49c6e-347c-dc64-8b9f-dc72ab0585d3] terraform_data.raw_zone: Destruction complete after 0s Apply complete! Resources: 1 added, 0 changed, 1 destroyed.
Self-studyignore_changes and replace_triggered_by3 min▶

ignore_changes removes listed attributes from the comparison, or every attribute with all. It has honest uses: an attribute another system manages on purpose, such as tags written by a cost tool or a size changed by an autoscaler, would otherwise be reverted on every apply. The danger is the wide version. ignore_changes = all means the config stops describing the object at all; a console edit stays forever and no plan will show it. The bench's anti-lever measures exactly that.

replace_triggered_by (Terraform 1.2 and later) goes the other way: it forces a replacement when some other resource or attribute changes, for objects that must be rebuilt when a dependency changes even though none of their own arguments did.

Which attributes are force-new is a provider fact, not a guess. Each provider's docs mark them. For example the AWS provider documents bucket on aws_s3_bucket as "Forces new resource", and Google's storage bucket schema sets ForceNew on name and location. Tags are updated in place on both. When in doubt, the plan's # forces replacement marker is the answer for your exact provider version.

Build-along · the bench

The plan simulator

★ 25 min · the main event

The simulator holds Larkspur's production state and a config you can edit. Every time the config or the state changes, it parses the config, diffs it against the state using each type's force-new rules, applies the lifecycle settings and moved blocks, and computes the apply order as a topological sort of the dependency graph. Nothing is looked up from a table of answers. Work down the ten rungs in order, and for each one say what the summary line says, then what the second counter says, before you move on.

Read each rung in this order. The verdict line, then the two headline counters, then the plan text, then the apply order and the graph. On rung 4 the summary is "1 to add, 0 to change, 1 to destroy" and the second counter says 1 data-bearing zone destroyed; on rung 6 the summary and the counter are identical and only the apply order differs.

LiveWalking the ladder12 min▶

Rung 1, add one zone: 1 to add, nothing else; the serving zone has no dependencies, so the apply order is one step. Rung 2, rename raw to landing with no moved block: 1 to add, 1 to destroy, and 1 data-bearing zone destroyed. The new zone even has the same name; Terraform does not know it is the same thing, because the address changed and nothing said so. Rung 3, the same rename with a moved block: "No changes", and the plan says raw has moved to landing.

Rung 4, change raw's region: region is force-new, so 1 to add, 1 to destroy, 1 replacement, 1 zone holding data destroyed. The apply order is destroy the old object, then create the replacement. Rung 5, the same with prevent_destroy: the plan stops with "Instance cannot be destroyed"; the counters read 0 and nothing runs. Rung 6, the same with create_before_destroy: identical counts, the symbol becomes +/-, and the apply order flips to create the replacement, then destroy the deposed object. The data is still destroyed.

Rung 7, tags only: 0 to add, 1 to change, 0 to destroy; an in-place update. Rung 8, rename the curated bucket: curated's name is force-new, and the catalog's storage_root reads that name, so the catalog must be replaced too: 2 to add, 2 to destroy, 1 data-bearing zone destroyed. The apply order destroys the catalog before the zone it depends on, then creates the zone before the catalog. The grant on the catalog is untouched, because the catalog's own name did not change.

LiveThe anti-lever and the break button5 min▶

Rung 9: someone has added a vendor tag to raw in the console. With a plain config, the plan puts the tags back: 0 to add, 1 to change. Rung 10, the anti-lever: add ignore_changes = all to raw and the plan says "No changes", while the third counter, unmanaged drift, reads 1. Now press "Console edit": retention is cut from 30 to 7 days, the plan still says "No changes", and drift rises to 2. Press the same button on rung 1 and the plan grows instead, with drift at 0. The honest nuance is on the widget: ignore_changes on a single attribute that another system owns is a real tool; all on a data zone is a config that has stopped describing it.

The break button, "Shuffle declaration order", rewrites the config with its blocks in a different order. The plan and the apply order must not change, and they do not: order comes from the graph, never from the file. The canon behind this page checked five shuffles of every rung in two independent engines.

Part 3 · covers the dependency graph and apply order

The graph decides what happens first

3 min live

Terraform builds a graph from every reference in the config (an implicit dependency) and every depends_on (an explicit one). Apply walks it so that nothing is created before what it needs; destroy walks it backwards so that nothing is removed while something still depends on it. Steps with no path between them can run at the same time, up to ten by default.

LiveImplicit references, and depends_on as a last resort2 min▶

Writing storage_root = lake_zone.curated.name both passes a value and declares a dependency. HashiCorp's guidance is to rely on references like this, and to use depends_on only "as a last resort", for hidden dependencies Terraform cannot see, such as a job that must wait for a permission whose value it never reads. In the bench, the catalog's depends_on = [lake_zone.raw] is that kind of edge: it changes the order of creates and destroys, never a value.

You saw the same thing with the real CLI in session 1: terraform graph printed one edge from the file to the random id, and destroy removed the file first.

Self-studyParallel walks and why the bench lists ties by address2 min▶

Real Terraform walks the graph concurrently: -parallelism limits the number of concurrent operations and defaults to 10. When two steps have no path between them, as in rung 2 (create landing, destroy raw), they may run at the same moment, and log lines can appear in either order between runs. The simulator has to print one list, so it breaks ties by address; that tie-break is the only thing on the widget not taken from Terraform's rules, and the widget says so.

Part 4 · covers policy as code, blast radius and the runner's permissions

A reviewer's checklist, partly automated

3 min live

A person reading plans will eventually skim one. Policy as code puts the rules that must never be skimmed into a program that reads every plan: HCP Terraform supports Sentinel, HashiCorp's own policy language, and Open Policy Agent with its Rego language. Writing those policies is beyond these pages; knowing what to ask of them is not.

LiveBlast radius and cost, in plain questions2 min▶

Blast radius is how much one plan can break. Ask: how many resources does this state file hold, and does a mistake in it reach production data? Smaller states, split by environment and by layer (session 6), keep the radius small; one giant state for everything means every plan is a plan against everything. Cost is the other quiet line: a plan that adds a warehouse or changes a size class changes the bill, and cost-estimation tools read the same plan JSON as policy tools.

Self-studyLeast privilege for the Terraform runner2 min▶

Whatever identity runs terraform apply can do anything its permissions allow, whatever the plan says. Give the pipeline's role only the services and resource names its configuration manages, keep a separate role per environment so a dev pipeline cannot touch prod, and keep a read-only role for plans on pull requests. Designing the roles themselves, and access for the people and tools that use the data, belongs to Data Access Control ↗; here the point is only that the runner is the outer fence on every plan.

Real world

The rule a team writes after its first lost bucket. The first policy many data teams adopt is the one rung 2 argues for: any plan that deletes or replaces a storage resource fails unless the pull request carries an explicit, reviewed exception. It turns the bench's second counter into a gate. Whether to write it in Sentinel or OPA depends on where the team runs Terraform, which session 6 covers.

Check yourself

Three questions

Clear all three and session 5 gets stamped in your passport.

1 · A pull request renames lake_zone.raw to lake_zone.landing and the plan says "Plan: 1 to add, 0 to change, 1 to destroy." What should the reviewer ask for?

Without a moved block Terraform sees an unrelated new resource and a removed one, so the raw zone is destroyed and an empty one created. The moved block re-addresses the existing object in state (bench rung 3: No changes). C still destroys the data, just later; D hides the zone from future plans.

2 · On the bench, rung 6 adds create_before_destroy to the region change. What changes compared with rung 4?

create_before_destroy changes when the old object goes, not whether it goes. The new zone is still a new, empty object. B describes prevent_destroy (rung 5); C would need the attribute to be in-place, like tags (rung 7).

3 · You press "Shuffle declaration order" on any rung. Why do the plan and the apply order stay exactly the same?

The graph is the same whatever the file order, so the topological sort is the same. Alphabetical order is only the simulator's tie-break between steps with no path between them; real Terraform runs those in parallel.
