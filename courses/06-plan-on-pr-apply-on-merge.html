Part 1 · covers workspaces against per-environment directories

Two ways to hold dev and prod, and why directories win for data

5 min live

CLI workspaces let one directory keep several states, one per workspace, under the same backend. Per-environment directories give each environment its own small root configuration and its own backend, calling the same shared module. Both reuse code. Only one keeps the environments apart where it matters: in credentials, in state and in the blast radius of a mistake.

LiveWhat a workspace really is3 min▶

Every initialised directory starts with one workspace called default. terraform workspace new dev creates another state for the same configuration in the same backend, and terraform.workspace lets the config read which one is selected, as the build-along does. HashiCorp's own page is direct about the limits: workspaces in one directory use the same backend, and "Workspaces alone are not a suitable tool for system decomposition". Its recommended alternative is reusable modules with a separate root configuration and backend per deployment.

For a data platform the difference is not tidiness. Prod holds the data. If the same person, pipeline and credentials can reach both states, the only thing between a dev experiment and the prod lake is which workspace a shell has selected.

Self-studyDirectories per environment, in practice3 min▶

Larkspur's layout becomes modules/data-zone/ (session 4), envs/dev/ and envs/prod/. Each env folder holds a short main.tf calling the module with that environment's values, its own backend block pointing at its own state, and its own lock file. Pipelines for prod run with a role that can touch only prod. The duplication is a few lines per environment, and it is deliberate.

Teams with many environments sometimes add a wrapper tool such as Terragrunt to generate those small root configs; that is beyond these pages. HCP Terraform also uses the word workspace, for its own unit of state and runs organised into projects (exam objective 8c); do not confuse it with terraform workspace new on the CLI.

Real world

The wrong shell. A pattern most platform teams can describe from memory: an engineer finishes testing in dev, opens another terminal to check something in prod, comes back, and applies in the terminal that is now pointed at prod. With directories and per-environment roles, that apply fails for lack of permission instead of succeeding against the wrong lake.

Part 2 · covers plan on pull request, apply on merge

The gate: a plan for every change, an apply only after review

5 min live

The workflow most teams converge on has two halves. On every pull request, a pipeline formats, validates and plans, with a read-only role, and puts the plan where reviewers can read it. Only when the pull request is merged does a pipeline with write access apply, from the reviewed code. Nobody applies from a laptop. The plan a reviewer approved and the change that happens are tied together by the branch, and checked by Terraform itself when the state has moved.

LiveThe gate in GitHub Actions4 min▶

HashiCorp publishes an action, hashicorp/setup-terraform (v4 is the current major), that installs the CLI in a GitHub Actions job; OpenTofu's equivalent is opentofu/setup-opentofu (v2). A minimal two-job workflow for one environment directory looks like this. It is shown, not run: it needs a repository, a remote backend and a cloud role, none of which these pages use.

★ .github/workflows/terraform-prod.yml · shown, not runname: terraform-prod on: pull_request: paths: ["envs/prod/**", "modules/**"] push: branches: [main] paths: ["envs/prod/**", "modules/**"] jobs: plan: if: github.event_name == 'pull_request' runs-on: ubuntu-latest defaults: { run: { working-directory: envs/prod } } steps: - uses: actions/checkout@v4 - uses: hashicorp/setup-terraform@v4 - run: terraform fmt -check -recursive - run: terraform init -input=false - run: terraform validate - run: terraform plan -input=false -out=tfplan # credentials here: a READ-ONLY role for prod apply: if: github.event_name == 'push' runs-on: ubuntu-latest defaults: { run: { working-directory: envs/prod } } steps: - uses: actions/checkout@v4 - uses: hashicorp/setup-terraform@v4 - run: terraform init -input=false - run: terraform plan -input=false -out=tfplan - run: terraform apply -input=false tfplan # credentials here: the WRITE role for prod, main branch only

The apply job plans again from the merged code and applies that exact saved plan. Two details carry the safety: the roles differ between the jobs, and apply tfplan applies a file, so it cannot quietly pick up a different change than the plan it just printed. Pinning action versions you have checked, and posting the plan text as a pull-request comment, are the usual next steps.

LiveWhy a saved plan goes stale2 min▶

A saved plan records the state it was computed against. If anything writes that state before the plan is applied, another merge or a teammate's apply, Terraform refuses to apply the old plan. The build-along produces this for real. It is the property that makes "plan, review, apply the reviewed plan" safe to run with more than one person merging.

★ Real run · a stale saved plan$ terraform apply prod.tfplan Error: Saved plan is stale The given plan file can no longer be applied because the state was changed by another operation after the plan was created.
Self-studyWhen the pipeline fails: verbose logs2 min▶

The Associate exam's objective 7c asks when and how to use verbose logging. Setting the TF_LOG environment variable to a level such as DEBUG makes Terraform write timestamped internal logs to standard error. On the build-along folder, a plain terraform validate printed 2 lines; with TF_LOG=DEBUG it printed 50, starting like this:

★ Real run · TF_LOG=DEBUG (first 3 lines)$ TF_LOG=DEBUG terraform validate 2>&1 | head -3 2026-11-03T12:35:48.449+0800 [INFO] Terraform version: 1.17.1 2026-11-03T12:35:48.449+0800 [DEBUG] using github.com/hashicorp/go-tfe v1.112.0 2026-11-03T12:35:48.449+0800 [DEBUG] using github.com/hashicorp/hcl/v2 v2.24.0

Use it to diagnose a provider or backend error, then turn it off: debug logs are long, and they can include details of your configuration that do not belong in a shared CI log.

Part 3 · covers HCP Terraform, OpenTofu and the licence split

Where Terraform runs, and which Terraform

5 min live

Since 2023 a data team choosing infrastructure-as-code tooling makes two decisions where there used to be one. Where do runs happen: on your own pipelines, or on HCP Terraform, HashiCorp's hosted service? And which engine: Terraform, now under the Business Source License and owned by IBM, or OpenTofu, the open-source fork. The facts below were read at source on 3 November 2026; this area moves, so check them again before relying on them.

LiveWhat BSL 1.1 means for a data team3 min▶

On 10 August 2023 HashiCorp announced it was moving future releases from the Mozilla Public License v2.0 to the Business Source License 1.1. Terraform's LICENSE file names the boundary: version 1.6.0 and later. Version 1.5.7 is the last release under MPL 2.0. The licensor named in that file is now IBM.

For a data team using Terraform to manage its own platform, HashiCorp's announcement says end users can continue to copy, modify and redistribute the code. The restriction sits in the licence's Additional Use Grant: you may not offer the licensed work to third parties on a hosted or embedded basis to compete with IBM's paid versions. Each version converts to MPL 2.0 four years after it is published. Where the line falls for a consultancy or a platform vendor is a question for a lawyer, not a course page; HashiCorp's licence FAQ could not be read at source for this page, so it is not quoted here.

Real world

The procurement question. After August 2023 many platform teams were asked by legal or procurement whether the licence change affected them. For a team running Terraform on its own infrastructure, the answer in HashiCorp's own announcement was that end users can keep using it; the teams that had to look harder were those embedding or hosting Terraform as part of a product they sell. Some teams moved to OpenTofu for the open licence and governance, some stayed for HCP Terraform's features; both are reasonable, and the choice is about the team's situation, not about one being correct.

Build-along

The gate, rehearsed on your laptop

★ 22 min · everyone builds

A pipeline is only the same commands run by a machine, so you can rehearse every one locally. Make a fresh folder with the config below; it uses terraform.workspace so you can see what workspaces do before deciding not to rely on them for prod. Every output was really run with Terraform 1.17.1; your ids will differ.

Write a deliberately untidy config. Save as main.tf, keeping the uneven spacing; step 2 is about catching it. Run terraform init once.

★ Step 1 · main.tfterraform { required_providers { local = { source = "hashicorp/local", version = "~> 2.5" } } } resource "local_file" "zone" { for_each = toset(["raw","curated","serving"]) filename = "${path.module}/lake/larkspur-${terraform.workspace}-${each.key}/ZONE.txt" content = "zone=${each.key} env=${terraform.workspace}\n" }

The formatting gate. fmt -check changes nothing; it lists unformatted files and exits non-zero, which fails a pipeline step. -diff shows what it would change. Then fix it and check again.

★ Step 2 · terraform fmt$ terraform fmt -check -diff main.tf --- old/main.tf +++ new/main.tf @@ -4,7 +4,7 @@ } } resource "local_file" "zone" { - for_each = toset(["raw","curated","serving"]) + for_each = toset(["raw", "curated", "serving"]) filename = "${path.module}/lake/larkspur-${terraform.workspace}-${each.key}/ZONE.txt" - content = "zone=${each.key} env=${terraform.workspace}\n" + content = "zone=${each.key} env=${terraform.workspace}\n" } [exit 3] $ terraform fmt main.tf $ terraform fmt -check [exit 0]

The validation gate. validate checks syntax, references and types without touching state or providers' real objects.

★ Step 3 · terraform validate$ terraform validate Success! The configuration is valid.

See what workspaces are. Two workspaces, two states, one directory and one backend. Note that workspace new also switches you to the new one, which is exactly the trap Part 1 describes.

★ Step 4 · workspaces$ terraform workspace new dev Created and switched to workspace "dev"! $ terraform workspace new prod Created and switched to workspace "prod"! $ terraform workspace list default dev * prod $ terraform workspace select dev Switched to workspace "dev".

Plan to a file, apply the file. This is the apply job's pattern: the plan is saved, and apply runs that exact plan instead of computing a new one.

★ Step 5 · saved plan (trimmed)$ terraform plan -out=dev.tfplan ... Plan: 3 to add, 0 to change, 0 to destroy. ... Saved the plan to: dev.tfplan ... terraform apply "dev.tfplan" $ terraform apply dev.tfplan local_file.zone["raw"]: Creation complete after 0s [id=2d18145fe7adc7af527ec22fec11794e1716e524] local_file.zone["serving"]: Creation complete after 0s [id=6bd6387a15ae8f03b6f60d561a6d5bd2f4f73559] local_file.zone["curated"]: Creation complete after 0s [id=1901e695492251a098080c221d12e05213c0a83b] Apply complete! Resources: 3 added, 0 changed, 0 destroyed. $ ls lake larkspur-dev-curated larkspur-dev-raw larkspur-dev-serving $ ls terraform.tfstate.d dev prod

Make a plan go stale. Select prod and save a plan. Then, standing in for a teammate's merge, apply prod directly. Now try to apply your saved plan: Terraform refuses, because the state it was computed against no longer exists.

★ Step 6 · the stale plan (trimmed)$ terraform workspace select prod Switched to workspace "prod". $ terraform plan -out=prod.tfplan ... Plan: 3 to add, 0 to change, 0 to destroy. Saved the plan to: prod.tfplan # meanwhile, someone else applies prod first $ terraform apply -auto-approve ... Apply complete! Resources: 3 added, 0 changed, 0 destroyed. $ terraform apply prod.tfplan Error: Saved plan is stale The given plan file can no longer be applied because the state was changed by another operation after the plan was created.

Write the workflow file you would commit. Copy the YAML from Part 2 into .github/workflows/ of a practice repository and change the paths to your layout. Leave it unrun until you have a remote backend and two roles; the point today is to read every step and know which command above it runs.

★ Step 7 · what each job runspull_request -> fmt -check, init, validate, plan -out (read-only role) merge to main -> init, plan -out=tfplan, apply tfplan (write role) stale plan -> the job fails; re-run it to plan again

Clean up. Run terraform destroy -auto-approve in each workspace, then terraform workspace select default and terraform workspace delete dev and prod. Everything here was local files, so nothing outside the folder was touched.

Check yourself

Three questions

Clear all three and session 6 gets stamped in your passport.

1 · Larkspur wants dev and prod managed from one repository. Which layout keeps a dev mistake from reaching the prod lake?

Workspaces do separate state, but they share a backend and usually the same credentials, so the selected workspace is the only fence; HashiCorp says they alone are not suitable for system decomposition. Separate directories separate state, backend and permissions while still sharing the module code.

2 · A pipeline saved a plan for prod, then another merge applied first. What happens when the pipeline runs terraform apply on its saved plan?

A saved plan is tied to the state it was computed from. Refusing a stale plan is what makes "apply exactly the reviewed plan" safe when several people merge. D would break that promise, because the applied change would differ from what anyone read.

3 · Which statement about Terraform's licence and OpenTofu is accurate?

The LICENSE file draws the line at 1.6.0. HashiCorp's announcement said end users can continue to use and modify the code; the restriction targets hosted or embedded competing offerings. OpenTofu is both LF-formed and, since 23 April 2025, a CNCF Sandbox project, not Graduated.
