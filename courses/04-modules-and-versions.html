Modules and versions

By now Larkspur has three lake zones for dev. Prod needs the same three, and the fastest way to get them is to copy the file and change a word, which is how two environments quietly stop matching. A module is the alternative: one folder that describes a zone once, called as many times as you need with different inputs. Tonight you write that module, call it for dev and prod, and learn the two things that keep it stable across laptops and pipelines: version constraints, and the lock file that records what they resolved to.

Part 1 · covers module structure, inputs, outputs and variable scope

A module is a folder with a contract

5 min live

Every Terraform directory is already a module: the one you run commands in is the root module. A child module is any other folder of .tf files that the root calls with a module block. What makes it reusable is the boundary. Values go in through variables, values come out through outputs, and nothing else crosses in either direction.

LiveA module is a folder with a contract3 min▶

By convention a module folder holds variables.tf (its inputs), main.tf (what it builds), outputs.tf (what it hands back) and a README that tells the next person what the inputs mean. Terraform does not care about the file names; people do, and a reviewer who knows where to look reviews faster.

Scope is strict in both directions. Inside modules/data-zone, the code can read var.env, var.zone and var.retention_days, and nothing from the root: not local.zones, not the other module call. The caller passes values in as arguments of the module block and reads values out as module.dev_zone["raw"].name. A local or a resource inside the module is invisible to the caller unless an output exposes it.

State, though, sees everything, with a longer address. The marker file for the dev raw zone lives at module.dev_zone["raw"].local_file.marker: module call, for_each key, then the resource address you already know from session 1.

Self-studyComposition over one giant module4 min▶

The tempting design is one module called platform with forty inputs that builds everything. It is hard to read, hard to test, and every change to it touches everything that calls it. The steadier pattern is small modules that each do one job, a zone, a catalog, a grant, composed in a root config that wires their outputs to each other's inputs. HashiCorp's own advice on separating environments points the same way: reusable modules for the common elements, and a separate root configuration per deployment.

Small modules also shrink the blast radius of a change, a reviewer's first question in session 5: a change inside data-zone can only touch zones.

Modules come from more than local folders. A source can be a local path such as ./modules/data-zone, or an address in a module registry. Only registry modules accept a version argument in the module block. A local path has no version: it is whatever is on disk in the same commit, which is exactly why Larkspur keeps its module in the same repository for now.

Real world

The copy that drifted. A familiar pattern in data teams: the prod configuration started as a copy of dev, then each got its own fixes. A year later a retention rule exists in one and not the other, and nobody can say whether that was a decision. With one module and two calls, the only differences between environments are the arguments in the module blocks, and a reviewer can read all of them on one screen.

Part 2 · covers version constraints and the dependency lock file

Constraints say what is acceptable; the lock file says what was chosen

5 min live

A version constraint is a promise about what you are willing to run. Each module states its own, the root states another, and terraform init has to find one release of each provider that satisfies all of them at once. It then writes the answer into .terraform.lock.hcl, so the next init, on your laptop or in a pipeline, makes the same choice.

LiveReading a constraint3 min▶

Seven operators cover every case. = allows one exact version and cannot be combined with other conditions. != excludes one exact version. > and >= ask for newer, < and <= for older, and a comma means "and". The one worth memorising is ~>, which allows only the right-most version component to increment.

HashiCorp's own examples make it concrete. ~> 1.0.4 allows 1.0.5 and 1.0.10 but not 1.1.0. ~> 1.1 allows 1.2 and 1.10 but not 2.0. So the more digits you write, the tighter the range.

In tonight's build-along the module asks for >= 2.4, < 3.0 and the root asks for ~> 2.5. init combines them into one line, ">= 2.4.0, ~> 2.5, < 3.0.0", and installs v2.9.1, the newest release that satisfies all three conditions. That line is printed by the real run in step 4.

LiveThe lock file pins providers, not modules3 min▶

.terraform.lock.hcl records, for each provider, the exact version init selected, the constraints it was selected against, and checksums of the package. The next init reuses that selection instead of looking for something newer, so every laptop and pipeline gets the same provider. HashiCorp's guidance is direct: include this file in your version control repository. Here is the real entry from tonight's run:

★ Real run · .terraform.lock.hcl (trimmed)# This file is maintained automatically by "terraform init". # Manual edits may be lost in future updates. provider "registry.terraform.io/hashicorp/local" { version = "2.9.1" constraints = ">= 2.4.0, ~> 2.5, < 3.0.0" hashes = [ "h1:OZGJN0LSSat5QIxZPxDXtVr4XpHb2oG7cVKJhSqBFIE=", "zh:25606c7a5e308144fb627f6e31611bb52ff72bb9ae2d27af39673ab1a6b3c1bf", ...

Notice what is missing: there is no entry for data-zone. The docs say it plainly: the lock file tracks only provider dependencies, and Terraform does not remember version selections for remote modules. If you call a registry module, pin it with the version argument in the module block, because nothing else will. When you do want a newer provider inside your constraints, run terraform init -upgrade and review the lock file change in the pull request like any other change.

Self-studyWhen no version fits3 min▶

Constraints can contradict each other or the registry. Ask for a major version that does not exist and init stops before anything is created. This is the real error from a scratch config that asked for hashicorp/local ~> 3.0, when the newest release is in the 2.x line:

★ Real run · the impossible constraintError: Failed to query available provider packages Could not retrieve the list of available versions for provider hashicorp/local: no available releases match the given constraints ~> 3.0

The same message appears when two modules want ranges that do not overlap, because init intersects before it searches. The error itself tells you the next move, terraform providers, which prints which module asked for what. Step 5 of the build-along shows that tree.

Real world

The major release nobody chose. Provider majors arrive with real changes: hashicorp/aws 6.0.0 added a region argument to most resources, for example. A team whose config sets no upper bound, and whose lock file is not committed, picks up a new major the next time a fresh machine runs init, and the first sign is an unfamiliar plan. A ~> constraint plus a committed lock file turns that surprise into a deliberate pull request.

Part 3 · covers the same module on real data platforms (shown, not applied)

One zone interface, four platforms underneath

5 min live

The data-zone module's contract, env and zone in, name out, says nothing about where a zone lives. Swap the resource inside and the same contract can create an object storage bucket, a warehouse database or a lakehouse catalog. What changes is the provider, its version, and which arguments force Terraform to destroy and recreate the object, which is the thing a data team most needs to know before wiring a module to data that matters.

LiveOne zone module, four providers4 min▶

Each box below is the resource you would put inside modules/data-zone/main.tf for one platform. They are shown, not applied: they need cloud accounts, and each needs more arguments than the ones listed here. Versions come from the public registry on 2026-11-03; provider majors move, so re-verify before relying on them.

Shown, not applied · AWS object storage# provider: hashicorp/aws, major 6 at the time of writing resource "aws_s3_bucket" "zone" { bucket = "larkspur-${var.env}-${var.zone}" # forces new resource region = "eu-west-1" # per-resource region, added in 6.0.0 # other required arguments omitted }

On AWS, bucket is marked "Forces new resource" in the provider docs: rename a zone and Terraform plans to destroy the bucket and create a new one. Provider 6.0.0 added a region argument to most resources, so one configuration can place resources in more than one region.

Shown, not applied · Google Cloud Storage# provider: hashicorp/google, major 8 at the time of writing resource "google_storage_bucket" "zone" { name = "larkspur-${var.env}-${var.zone}" # ForceNew in the schema location = "EU" # ForceNew in the schema # other required arguments omitted }

On Google Cloud, the docs say a bucket's location cannot be changed after creation, and the provider's source schema sets ForceNew on both name and location.

Shown, not applied · Snowflake database# provider: snowflakedb/snowflake, major 2 at the time of writing resource "snowflake_database" "zone" { name = "LARKSPUR_${upper(var.env)}_${upper(var.zone)}" # unique in the account # other required arguments omitted }

On Snowflake, name must be unique for your account. Note the source address: the provider moved from the Snowflake-Labs organisation to snowflakedb in 2025. Existing state still points at the old address, and the migration guide's fix is one command, terraform state replace-provider Snowflake-Labs/snowflake snowflakedb/snowflake. The provider documentation read for this page does not mark which snowflake_database arguments force replacement, so check the current docs before renaming one.

Shown, not applied · Databricks Unity Catalog# provider: databricks/databricks, major 1 at the time of writing resource "databricks_catalog" "zone" { name = "larkspur_${var.env}_${var.zone}" storage_root = "s3://larkspur-${var.env}-lake/${var.zone}" # change forces a new resource # other required arguments omitted }

On Databricks, a catalog is the top level of Unity Catalog's 3-level namespace. The docs say a change to storage_root forces creation of a new resource; name is not marked that way.

Self-studyrequired_providers in a multi-provider module3 min▶

A module that uses more than one provider lists each in its own required_providers block, with a source address of the form namespace/type and a constraint per provider. The namespace is not decoration: hashicorp/aws, snowflakedb/snowflake and databricks/databricks are three different publishers, and the Snowflake move above shows that a namespace can change under a config that never did.

The pattern for modules is a wide constraint, such as >= 2.4, < 3.0 in tonight's module, so the module works for many callers, and a tighter one in the root, such as ~> 2.5, where the team decides what it actually runs. This is the Associate exam's objective 2c, writing configuration with multiple providers. Session 1's config, with hashicorp/local and hashicorp/random side by side, was already a small example; provider aliases, which let one provider appear twice with different settings, are not covered on these pages.

Real world

A warehouse and a lakehouse from one repository. A common data-platform shape: object storage in one cloud, warehouse databases in Snowflake, and catalogs in Databricks, all provisioned from the same repository and reviewed in the same pull requests. The modules give each a consistent naming contract, so larkspur_prod_curated means the same zone everywhere. The platforms themselves, how a warehouse or a lakehouse should be modelled, are taught in Learn Data Warehouse with Phoebe and Learn Databricks with Phoebe; the AWS services in Learn AWS with Phoebe. This session's job is only to provision them as code.

Build-along

One data-zone module, dev and prod

★ 22 min · everyone builds

Priya writes the zone once and calls it twice, each time with for_each over the same three zones. Start a fresh, empty folder. Every output below was really run with Terraform 1.17.1 and hashicorp/local 2.9.1; ids, hashes and times will differ on your machine.

Write the module's inputs. Create modules/data-zone/variables.tf. Three variables, each with a type and a description; retention_days has a default, so a caller may leave it out.

★ Step 1 · modules/data-zone/variables.tfvariable "env" { type = string description = "Environment name, dev or prod" } variable "zone" { type = string description = "raw, curated or serving" } variable "retention_days" { type = number description = "How long files stay in the zone" default = 30 }

Write what it builds and what it returns. The module states its own wide provider constraint. path.root is the root module's folder, so every zone lands under one lake/ no matter which module call made it. The outputs are the only two values a caller will ever see.

★ Step 2 · modules/data-zone/main.tfterraform { required_version = ">= 1.5.0" required_providers { local = { source = "hashicorp/local", version = ">= 2.4, < 3.0" } } } locals { name = "larkspur-${var.env}-${var.zone}" } resource "local_file" "marker" { filename = "${path.root}/lake/${local.name}/ZONE.txt" content = "zone=${var.zone} env=${var.env} retention_days=${var.retention_days}\n" }
★ Step 2 · modules/data-zone/outputs.tfoutput "name" { value = local.name } output "path" { value = local_file.marker.filename }

Call it twice from the root. Save this as main.tf in the root folder. The retention per zone lives once, in locals.zones; dev and prod differ only in env. With for_each on a module call, module.dev_zone becomes a map of module instances, which is why the output loops over it.

★ Step 3 · main.tfterraform { required_providers { local = { source = "hashicorp/local", version = "~> 2.5" } } } locals { zones = { raw = 30 curated = 365 serving = 90 } } module "dev_zone" { source = "./modules/data-zone" for_each = local.zones env = "dev" zone = each.key retention_days = each.value } module "prod_zone" { source = "./modules/data-zone" for_each = local.zones env = "prod" zone = each.key retention_days = each.value } output "zone_names" { value = concat([for m in module.dev_zone : m.name], [for m in module.prod_zone : m.name]) }

Initialise. There is a new first stage: "Initializing modules...". Then read the "Finding" line: init has merged the module's constraint with the root's into one, and picked v2.9.1 from inside it.

★ Step 4 · terraform init (trimmed)$ terraform init Initializing the backend... Initializing modules... - dev_zone in modules/data-zone - prod_zone in modules/data-zone Initializing provider plugins... - Finding hashicorp/local versions matching ">= 2.4.0, ~> 2.5, < 3.0.0"... - Installing hashicorp/local v2.9.1... - Installed hashicorp/local v2.9.1 (signed by HashiCorp) Terraform has created a lock file .terraform.lock.hcl to record the provider selections it made above. Include this file in your version control repository so that Terraform can guarantee to make the same selections by default when ...

Ask who wants which provider. terraform providers prints the requirement tree: the root's constraint at the top, each module call's underneath. This is the command to reach for whenever init refuses a version.

★ Step 5 · terraform providers$ terraform providers Providers required by configuration: . ├── provider[registry.terraform.io/hashicorp/local] ~> 2.5 ├── module.prod_zone │ └── provider[registry.terraform.io/hashicorp/local] >= 2.4.0, < 3.0.0 └── module.dev_zone └── provider[registry.terraform.io/hashicorp/local] >= 2.4.0, < 3.0.0

Open the lock file. One provider block, with the version chosen, the merged constraints and the hashes. Search it for data-zone: you will not find it, because the lock file tracks providers only. Commit this file.

Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · A root config asks for hashicorp/local ~> 2.5. Which releases does that allow?

~> lets only the right-most component you wrote increment. With two components, 2.5, the minor version can rise, so 2.6 and 2.9.1 are allowed and 3.0 is not. C is the answer for ~> 2.5.0, which has three components; HashiCorp's own example is ~> 1.0.4, which allows 1.0.10 but not 1.1.0.

2 · Your root calls a module from a registry. Does .terraform.lock.hcl pin that module's version?

The docs are explicit that the lock file tracks only provider dependencies and that Terraform does not remember version selections for remote modules. Tonight's lock file had one provider block and no trace of data-zone. A local module has no version at all: it is whatever is on disk in the same commit.

3 · From the root, what can a caller read from inside module.dev_zone["raw"]?

Outputs are the module's only way out, which is why the root builds zone_names from m.name. The trap in B is that state does use long addresses like module.dev_zone["raw"].local_file.marker; that is how Terraform tracks the object, not something your configuration can read from outside.
